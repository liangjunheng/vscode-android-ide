# 项目工作流

## 强制约束

- 必须严格按照顺序依次进入门禁，并遵守每个门禁的全部强制性规则；门禁未完成、失败、阻塞或证据不足时，禁止进入或跳过后续门禁。
- 启动任何 subagent 前，主会话必须先创建与其对应的 task，并通过 task 记录、监听和收敛其状态；每 15 秒检查一次 subagent 状态，并修复异常状态；无对应 task，禁止启动或重启 subagent。
- 所有注释和回答必须使用中文。
- 仅当用户明确下达包含“强制”二字的命令时，才允许跳过任意门禁；否则不得跳过。

## 1. 分析门禁

先依据用户明确表述和现有事实，将任务准确分类；无法确定时必须询问，禁止猜测。

- **需求类**：明确目标、验收标准、边界、假设、入口、调用链、测试和验证方式。
- **bugfix 类**：先实际复现问题，记录版本、环境、前置条件、步骤、预期、实际结果和证据；定位根因、影响范围和回归测试。未复现或复现受阻时不得进入代码实现，并说明原因。

两类任务都必须明确成功/失败判据、变更范围、风险和验证成本。纯文档、格式或无行为变化的重命名不需要复现。

## 2. 代码实现门禁

### 强制性规则

- 进入下一门禁前，必须确认后续不再存在代码实现任务或关联工作；主会话、task、subagent 及其他执行项均已完成且无未完成项。
- 修改代码前必须重新读取相关代码，确认当前内容与调用关系，避免用户改动未同步导致逻辑不一致。
- 通过获取文档、测试与验证、注释、代码、联网搜索、知识库等一切关联点，提出三份可行方案；三份方案必须属于核心逻辑改动，评估后执行最优方案。
- 禁止使用兜底机制、回落机制、兼容性处理、版本号控制、令牌控制等类似逻辑，以及硬编码、削弱检查等代码实现方式。
- 严格限制非必要的延时、锁和吞错等实现方式；确需吞错时，必须打印 W 级别或更高级别日志。
- 在行为正确的前提下，优先采用单线程设计以减少锁的使用。
- 必要时允许重构以减少代码量，并清除关联的冗余逻辑和兼容性处理。
- 修改代码后，必须严格进行新增、删除和修改对应的注释、测试与验证设计。
- 完成代码实现后必须自检；发现问题立即修正，并重新执行受影响的测试和验证。

### 测试与验证设计强制性规则

- 按功能点拆分测试与验证；一个功能点对应一个文件或文件夹，不得混放无关功能。
- 设计方案时明确前置条件、所有复现路径、执行步骤、预期结果、成功/失败判据和测试范围，并与代码实现、注释及测试映射保持一致。
- 设计不完整或不一致时，先修正设计。
- 每个执行入口必须添加注释，完整说明该功能点的复现路径、测试范围和全部受影响对象，并按以下模板填写：

```rust
/// 功能点：说明本文件或文件夹覆盖的单一功能。
/// 受影响对象：列出所有受影响的代码函数、类、文档、数据及其他关联对象。
/// 复现路径：列出所有复现步骤、前置条件和输入。
/// 测试范围：说明覆盖的正常、边界、异常和回归场景。
/// 执行入口：说明测试或验证的入口函数、命令或脚本。
/// 预期结果：说明成功时应观察到的结果。
/// 判据：说明成功和失败的明确判断条件。
```

### 代码注释强制性规则

- 新增或修改函数必须补充准确中文注释，说明职责、输入、输出、前置条件和结果。
- 代码行为变化后，必须同步修正过时、错误或与实现不一致的注释。
- 注释中的“验证”必须关联所有相关的测试与验证设计。
- 函数注释统一使用以下模板，按实际情况填写并删除不适用项：

```rust
/// 功能：说明函数要完成的功能。
/// 输入：说明参数、来源和前置条件。
/// 输出：说明返回值、状态变化或副作用。
/// 验证：说明对应的可执行测试或验证命令。
```

## 3. 测试与验证门禁

### 适用范围

- 仅当本次任务实际修改代码时启动；未修改代码时不启动本门禁。

### 内置测试与验证规则

- 执行测试或验证前，必须先读取对应执行入口的注释，并以其中记录的复现路径、受影响对象、测试范围和判据为准。
- 由 subagent 执行已设计的测试和验证，记录命令、版本、前置条件、实际结果及成功/失败判据，并覆盖直接功能、边界、异常和回归场景。
- 测试或验证结果异常、不完整或不一致时，返回代码实现门禁；修正测试与验证设计时，必须同步修改对应执行入口注释，再重新执行受影响项目。

## 4. 独立评审代码门禁

### 适用范围

- 仅当本次任务实际修改代码时启动；未修改代码时不启动本门禁。

### 执行要求

- 任务异常、丢失、提前结束、超时或结果无效时，立即重新发起评审；未收到有效结果不得继续，平台持续异常时阻塞交付。
- 主 Agent 不得代替评审。

### 内置评审规范

- 评审结论必须基于可靠、明确、可复核的问题和证据，禁止猜测、推断或以不确定性作为 `FAIL` 依据。
- subagent 只审查本次变更及直接影响范围，不修改、不提交，并检查：

- 判断是否为核心逻辑改动
- 校验测试与验证结果
- 严格遵循代码实现门禁

评审结果必须包含每项 `PASS/FAIL`、文件位置、事实证据、未执行项、阻塞、风险、修正建议和总体结论。存在未解决的 `FAIL`、关键未执行项或无效证据时，总体结论必须为 `FAIL`；必须根据失败项回到对应门禁，完成修正后重新执行受影响的测试、验证和独立评审代码，不得直接交付。

## 5. 交付门禁

仅当适用门禁、测试、验证和独立评审代码全部通过，且没有无关改动时，才能执行 `git commit` 并交付；未执行项、阻塞和剩余风险必须明确说明，未通过时禁止提交。
