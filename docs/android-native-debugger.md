# Android Native Debugger

## Scope and Design

Only the Native backend is enabled. The Android parent session starts a `type: "lldb"` child owned by CodeLLDB, which connects its Android remote platform to an NDK `lldb-server`. No Java/Kotlin debug engine, Maven build or JAR is restored. The original source is `E:/vscode-android-debug-main` (nisargjhaveri/vscode-android-debug); Native source provenance is recorded beside the imported snapshot.

The integration preserves device/ABI selection, NDK server discovery/deployment, attach and launch, native configuration forwarding, ART signal handling, symbol search paths and optional JDWP VM resume. Host-only lifecycle corrections must remain explicit. Existing external launch configurations are not converted into built-in sessions.

## Automatic Metadata Design

User update: resolve Native package and ABI from the selected Gradle variant/APK/device before prompting; show a field picker only for normally unavailable or ambiguous metadata. Explicit valid configuration remains an override. ADB/Gradle failures propagate and never become an apparently successful default.

The implementation gate was preceded by checking these executable paths: Existing Build output metadata and optional unknown package forwarding (android-build.test.js); workspace-scoped lazy Build callback and explicit overrides (native-codelldb.test.js); canonical process ABI hint forwarding (device-explorer-controller.test.js); provider-resolved package/PID event identity (android-debugger-configurations.test.js); automatic device primary ABI, ambiguous/missing fallback, cancellation and error propagation (native-autodetect.test.js); actual device picker/process discovery at the Appium/VSCode boundary (native-picker.test.js and native-discovery.test.js). No ABI is inferred only from a 64-bit phone when an installed package reports a 32-bit ABI.

The previous independent review returned FAIL for JDWP cleanup error preservation/close settlement and missing real device/process/picker coverage. These findings and the new automatic-selection rules must be corrected and validated on current content before the same reviewer is asked to re-review. The current direct regressions include controlled socket-close settlement and combined handshake/cleanup failures, real production picker/process discovery through boundary mocks, and strict query-error versus normally-missing behavior. Current validation results are recorded below; historical counts are not reused.

Package precedence is explicit configuration, existing metadata from the selected Gradle variant/APK, then exact or unique PID ownership. Entering built-in debug does not run Gradle to obtain missing metadata. Only unresolved/ambiguous ownership opens the installed-package picker. A shared UID never selects its first package arbitrarily. Build-to-Native passes complete ABI split constraints when present; universal or missing output filters leave ABI unknown.

ABI precedence is explicit canonical ABI/process hint, installed package primaryCpuAbi, then the compatible app/device intersection. A single compatible value is automatic; multiple candidates require selection. Empty device properties mean unknown and use app candidates, while a nonempty incompatible intersection is an error. Package/ABI picker cancellation terminates resolution. Explicit serial, selected workspace root, package and PID ownership are asserted through provider and caller tests.

The process command regression also covers sorting/PID mapping, cancellation and rejected getProcessList without an unresolved async Promise executor. The runtime regression distinguishes normal empty package output from rejected ADB commands and validates PID before shell use.

## Implementation Adaptations

The unmodified original source is stored under upstream/source with SHA-256 entries in upstream/SOURCE_LOCK.json. A direct hash comparison against E:/vscode-android-debug-main confirmed all 12 copied TypeScript files match their originals. The actual runtime now enters the migrated original upstream/src/debugAdapter.ts DebugAdapterDescriptorFactory/DebugAdapter, rather than a separately implemented host parent class. Original method names and Native attach/launch/resume ordering are retained; Native-only host and lifecycle patches remain explicit. The runtime closure under upstream/src retains the original Appium ADB operations, device/ABI providers, NDK layout, server deployment commands and JDWP VM.Resume packet. Java/profiler classes in shared original files are not registered.

Necessary host adaptations are: one Native-only configuration facade; default launcher Activity resolution; matching the launched package instead of the last unrelated JDWP process; shared project-local/original-settings toolchain resolution; fixed CodeLLDB child identity; asynchronous DAP error responses; and explicit ownership/rollback of child sessions, server sockets and JDWP forwarding. Appium is constructed with its public constructor and the selected executable because createADB would overwrite that executable with its SDK lookup. Manual VM resume now awaits its temporary connection cleanup rather than scheduling it later.

## Direct Debug Entry

Latest user correction: selecting built-in Native must open VS Code Run and Debug and start debugging without rebuilding. The former Build path ran install<Variant> and discoverVariantSources before every debug start; the former process Attach path also queried the Gradle model for known packages. These were unnecessary prerequisites for debugging an existing installed app.

Build Native debug now performs only the existing online-device check and reads existing selected APK metadata for package/ABI hints. It does not assemble, install or query AGP sources. Processes Native Attach forwards the current device/PID/package and canonical ABI directly, without calling the project-model resolver. Explicit Build, Install and Run controls retain their original Gradle behavior, as do external debug configurations. An explicit user apkPath or preLaunchTask remains a user-requested action; no implicit build is inserted by the built-in entry.

The shared Native starter awaits workbench.view.debug before startDebugging, then rechecks the caller AbortSignal and workspace trust. Navigation failure or cancellation creates no session. Analysis/test design was checked before implementation: android-build.test.js must assert zero additional Gradle/model calls for built-in Debug and preserve explicit actions/external configs; device-explorer-controller.test.js must assert zero resolver calls for known and unknown packages while preserving PID revalidation; android-debugger-configurations.test.js asserts view-before-start, external view isolation, original navigation errors, cancellation/trust failure and listener ownership. The targeted entry/provider batch passed 85/85 and affected UI batch passed 33/33. ## Built-In Configuration Name

The programmatic configuration object starts a named session but does not by itself contribute an entry to the Run and Debug configuration picker. NativeAndroidConfigurationProvider now provides one independent [built-in] Android Native launch configuration through both initial configuration discovery and the official Dynamic trigger. The dynamic registration intentionally exposes only provideDebugConfigurations, so device/ABI/server resolution is not performed twice. Existing user launch configurations and their selected item are not rewritten; no private workbench selection command or second debug start is used.

Before implementation, the name-display test design was checked against native-codelldb.test.js: initial and dynamic entry points must return the same Native name, independent option objects, exactly one dynamic registration, no duplicate resolver, and zero SDK/ADB/server work at discovery. device-manager-ui.test.js and the actual VSIX activation fixture assert the dynamic name is registered by the real source/production bundle. The configuration picker item is tested through the supported provider contract, not claimed as a captured real VS Code GUI screenshot.

## Project-built Native Symbols

Native symbol loading uses project build-target records and ELF debug information instead of a saved manual file whitelist. All unique project-built libraries for the selected ABI load automatically. Duplicate library names automatically use the newest file modification time; ties use deterministic path ordering. No picker or manual whitelist is used, and every session reevaluates the current build outputs. The resulting relative file list is written atomically to the current project's `.vscode/android-native-symbols.json` for inspection only. The current project/package/ABI's old manual selection is removed without deleting another project's records. Precompiled, external and packaging-copy libraries are not automatically loaded, and missing build evidence does not open a manual external-library picker.

Executable checks: `node --test tests/native-project-libraries.test.js tests/native-symbol-selection.test.js tests/native-codelldb.test.js`. Discovery tests validate build provenance, ELF/DWARF and ABI; selection tests validate automatic loading, duplicate cancellation and stale-record correction; parent-session tests verify exact module commands. These checks do not prove the local binary matches the installed APK or that source breakpoints bind on a real device.

## Remaining Limits

Real-device breakpoint, step and variable inspection require an authorized Android device, a debuggable APK and matching unstripped native symbols; these were not performed. Device/ADB behavior is covered through boundary mocks, not claimed as a real-device success. NDK discovery preserves the original reverse lexicographic folder selection and does not parse Gradle ndkVersion/ndkPath or local.properties to choose the project build NDK. Explicit debugger.ndkPath is the deterministic project-local override.
